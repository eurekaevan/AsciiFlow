# Stage 5.2A: P010LE processing foundation

This is an internal processing format, not a media support announcement.
The production CLI still rejects 10-bit HEVC and AV1 transcoding, while the
internal decoder can now produce canonical P010LE from 10-bit BT.709 SDR media.
The H.264, HEVC Main and AV1 Profile0 output encoders still accept only NV12 8-bit.
At the Stage 5.2A seal, there was no qualified P010 VAAPI decode or DRM PRIME
input import. [Stage 5.2B](stage5.2b-p010-decode-validation.md) later qualified
those internal paths on Intel Arc; [Stage 5.2C-1](stage5.2c1-p010-output-interop.md)
qualified diagnostic P010 Vulkan→VAAPI output interop on the same device.
Neither stage implements a production 10-bit encoder, HDR interpretation or
a CLI pixel-format option.

## Portable frame contract

`PixelFormat::{Nv12,P010Le}` is a Core identity without FFmpeg, Vulkan or DRM
constants. `HostFrame` owns a `Vec<u8>` in both cases. Width and height must be
non-zero and even; all size products and sums are checked before construction.
Planes are tightly packed, with no row padding:

| Format | Y stride | UV stride | Y bytes | UV bytes | Total bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| NV12 | width | width | width × height | width × height / 2 | width × height × 3 / 2 |
| P010LE | width × 2 | width × 2 | width × height × 2 | width × height | width × height × 3 |

P010LE Y is one little-endian 16-bit word per pixel. Its UV plane interleaves
little-endian U and V words for each 2×2 chroma block. Bits 15..6 contain the
10-bit code (0..1023); bits 5..0 are padding. CPU reads with
`u16::from_le_bytes(bytes) >> 6` and writes `(code << 6).to_le_bytes()`. Output
padding bits are always zero. No pointer cast, native-endian `u16` view or
floating-point conversion is used.

Frame color metadata is carried unchanged. P010LE describes code precision;
it does not imply HDR, BT.2020, PQ or HLG. P010LE with BT.709 SDR metadata is
a valid internal frame. The current background codes correspond to NV12 Y=16,
UV=128 and P010LE Y=64, UV=512; monochrome foreground Y is 235 or 940.

## CPU and Vulkan semantics

The CPU mapper accumulates 10-bit Y, U and V codes as integers, then divides
by the sample count. For glyph selection only, it reduces the completed 10-bit
Y mean with `mean10 >> 2` and indexes the existing 256-entry LUT. If an NV12
frame is expanded exactly by `sample10 = sample8 << 2`, its cell glyphs match
the NV12 frame. The extra active low bits of each P010LE cell mean remain
available to color rendering. The CPU mapper checks the worst-case 10-bit
cell sum before accumulating in `u64`.

The CPU renderer blends 10-bit foreground and background with the unchanged
R8 atlas coverage, using `(bg × (255 − a) + fg × a + 127) / 255` in `u32`.
Only the final store shifts the result into the high ten bits of a P010LE
word. Grayscale, color and FreeType all use the same atlas. The NV12 and P010LE
CPU loops are selected once per frame through separate const-generic code
paths.

Vulkan selects a separate P010LE map/render shader when its resources are
created. Input/output storage consists of 16-bit words, immediately promoted
to 32-bit for reduction and blend. P010LE map has a checked `u32` path for
normal cells and the existing `u64` fallback for oversized cells, using a
1023-per-sample bound. The render pass uses the existing host-generated
coordinate LUT, one 2×2 pixel block per invocation and an R8 glyph atlas.
There is no per-pixel runtime format branch. The resource key includes pixel
format, so switching NV12/P010LE rebuilds the appropriately sized buffers and
pipelines; the two-slot worker retains the same FIFO and drain semantics.

The P010LE SPIR-V uses `StorageBuffer16BitAccess` and
`StorageBuffer8BitAccess` (the latter for atlas coverage). It does not declare
`Int16` arithmetic, float or 64-bit division in the ordinary `u32` variant.
Vulkan device enumeration keeps its NV12 eligibility unchanged and records
`storageBuffer16BitAccess` separately; a device lacking it receives a P010LE
specific error at backend preparation.

## Validation and limits

Portable tests cover P010LE packing, zero padding, 2×2 through 1920×1080
layout, invalid geometry/overflow, CPU mapping/rendering, exact NV12-expanded
glyph identity, and retained low active luma/chroma bits. The Vulkan tests use
constant, gradient, checkerboard and deterministic pseudo-random frames;
compare mapped cells and final P010LE bytes against CPU for color and
grayscale; compare FreeType output; and drain 1, 2, 3 and 5 frames through two
slots. A 3000-frame synthetic two-slot reuse test checks order, pixels and
padding. These Stage 5.2A tests passed on lavapipe with Khronos Validation
enabled and zero reported Validation/VUID/synchronization errors. That
environment did not expose `/dev/dri`; later Intel Arc input and output
qualification are recorded in [Stage 5.2B](stage5.2b-p010-decode-validation.md)
and [Stage 5.2C-1](stage5.2c1-p010-output-interop.md).

All 96 generated debug and Release SPIR-V files, including the P010LE variants,
passed `spirv-val --target-env vulkan1.3` with zero errors. The P010LE `u32` shader
disassembly has no `OpTypeInt 64`, 64-bit divide/modulo or float conversion.

An opt-in Release benchmark processed 300 synthetic 1920×1080 P010LE frames
at ASCII width 80 on lavapipe. Its single-run observations were:

| Backend | FPS | GPU map timestamp | GPU render timestamp | Backend wall |
| --- | ---: | ---: | ---: | ---: |
| CPU | 46.21 | — | — | 21.638 ms/frame |
| Vulkan 1-slot | 120.79 | 1.468 ms/frame | 2.346 ms/frame | 7.583 ms/frame |
| Vulkan 2-slot | 133.08 | 1.765 ms/frame | 2.582 ms/frame | 20.906 ms/frame |

Two-slot backend wall includes overlapped queue residence and cannot be added
or compared directly to per-frame GPU timestamps; its throughput wall was
7.514 ms/frame. These software-driver numbers are a functional sanity check,
not Intel GPU performance evidence. The benchmark is reproducible through the
ignored `p010_synthetic_1080p_300_frame_benchmark` test.

For the existing NV12 path, three paired 300-frame Release runs on the same
lavapipe device used the retained Stage 5.1B H.264 input, software decode,
Vulkan processing and software H.264 encode. The old/new medians were
139.96/140.81 FPS (new +0.61%); all six MP4 SHA-256 hashes matched exactly
(`90026ef9b395bc2df45045b7401d8b11824d4735313c0eebdd394b2c2db7a7bf`).
This checks the unchanged NV12 shader path locally but does not replace the
Stage 5.1B Intel full-interop performance and H.264/HEVC/AV1 output baselines.
An additional 300-frame software-decode/CPU/software-encode run with the same
input produced the same SHA-256 with the retained old and new binaries; this
also covers the NV12 CPU mapper and renderer after adding P010LE dispatch.

At the Stage 5.2A seal, real Main10 HEVC and 10-bit AV1 fixtures failed at
input qualification with `10-bit video is not supported by the current 8-bit
NV12 pipeline`. The current CLI instead rejects their production conversion
because no 10-bit output path exists, before staging output creation. The
encoder factory and VAAPI probe reject a
P010LE descriptor before opening an output. This prevents the internal frame
format from silently activating a production 10-bit path. See
[Stage 5.2B](stage5.2b-p010-decode-validation.md) for software decode and
Intel VAAPI/DRM input qualification.
